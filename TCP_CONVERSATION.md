# TCP и HTTP как разговор двух друзей

Этот разбор основан на захвате из `tcp_ip_logs.txt`.

Представим, что клиент и сервер — два друга, которые разговаривают по телефону:

- **клиент** — `curl` с временным портом `49852`;
- **сервер** — HTTP-сервер на порту `12345`;
- **TCP** — телефонная служба, которая устанавливает звонок, нумерует переданные байты и следит за их доставкой;
- **HTTP** — содержание разговора: запрос, ответ, заголовки и тело.

TCP-соединение полнодуплексное: клиент и сервер могут одновременно передавать данные и независимо закрывать своё направление передачи.

## Обозначения tcpdump

| Обозначение | Флаги | Смысл |
|---|---|---|
| `[S]` | SYN | Предложение установить соединение |
| `[S.]` | SYN + ACK | Согласие установить соединение и подтверждение SYN |
| `[.]` | ACK | Подтверждение полученных данных или служебное сообщение о состоянии TCP |
| `[P.]` | PSH + ACK | Передача данных с просьбой быстрее отдать их приложению |
| `[F.]` | FIN + ACK | Завершение передачи в одном направлении |

Точка означает установленный флаг ACK. После установки соединения ACK присутствует почти во всех TCP-сегментах.

## 1. Клиент звонит серверу

```text
49852 > 12345: Flags [S]
seq 1199673994
```

Клиент говорит:

> Привет! Я хочу установить соединение. Начнём считать мои данные с номера `1199673994`.

`SYN` предлагает установить TCP-соединение. Вместе с ним клиент отправляет TCP options и сообщает, какие возможности он поддерживает. HTTP ещё не начался.

## 2. Сервер принимает звонок

```text
12345 > 49852: Flags [S.]
seq 2447710706
ack 1199673995
```

Сервер отвечает:

> Привет! Согласен установить соединение. Твоё предложение получил и следующим ожидаю номер `1199673995`. Мои данные будем считать с номера `2447710706`.

`SYN + ACK` одновременно:

- подтверждает SYN клиента;
- сообщает начальный sequence number сервера;
- передаёт TCP options сервера.

## 3. Клиент подтверждает ответ

```text
49852 > 12345: Flags [.]
ack 1
length 0
```

Клиент говорит:

> Хорошо, твой ответ получил. Мы соединены.

Полезных данных здесь нет: `length 0`. На этом TCP handshake завершён:

```text
Клиент → Сервер: SYN
Сервер → Клиент: SYN + ACK
Клиент → Сервер: ACK
```

После handshake `tcpdump` показывает удобные относительные номера вместо больших начальных sequence numbers. Поэтому дальше появляются значения `1`, `104` и `115`.

## 4. Сервер дополнительно сообщает своё состояние

```text
12345 > 49852: Flags [.]
ack 1
win 6380
length 0
```

Сервер повторяет:

> Соединение установлено. По-прежнему ожидаю от тебя данные начиная с номера `1`. Моё доступное окно — `6380`.

Это чистый служебный ACK от TCP-стека macOS. Он может быть связан с обновлением состояния или приёмного окна. По одной строке захвата точную внутреннюю причину определять не требуется.

Это не четвёртый этап handshake и не вызов `send()` из программы. Пакет сформировало ядро операционной системы.

## 5. Клиент задаёт HTTP-вопрос

```text
49852 > 12345: Flags [P.]
seq 1:104
ack 1
length 103
```

Клиент говорит:

> Передаю тебе 103 байта с номера `1` до номера `103`. После них следующим будет номер `104`.

В этих TCP-байтах находится HTTP-запрос:

```http
GET /health HTTP/1.1
Host: 127.0.0.1:12345
User-Agent: curl/8.7.1
Accept: */*
Connection: close

```

Если перевести его на обычный язык:

> Дай мне ресурс `/health`. Разговариваем по правилам HTTP/1.1. Я обращаюсь к серверу `127.0.0.1:12345`. Я — curl версии 8.7.1. Принимаю любой формат ответа. После ответа закрой соединение.

Пустая строка после заголовков соответствует разделителю `\r\n\r\n` и означает конец заголовков. Тела у запроса нет.

## 6. Сервер подтверждает доставку вопроса

```text
12345 > 49852: Flags [.]
ack 104
length 0
```

Сервер говорит:

> Все твои байты до номера `103` включительно получил. Следующим ожидаю байт `104`.

Это подтверждение доставки на уровне TCP. Оно ещё не означает, что HTTP-запрос обработан. Байты дошли до TCP-стека сервера, после чего приложение должно прочитать и обработать их.

## 7. Сервер отправляет HTTP-ответ

```text
12345 > 49852: Flags [P.]
seq 1:115
ack 104
length 114
```

Сервер говорит:

> Отправляю тебе 114 байт с номера `1` до номера `114`. После них следующим будет номер `115`. Твои байты до номера `103` я получил.

Внутри находится HTTP-ответ:

```http
HTTP/1.1 200 OK
Connection: close
Content-Type: text/plain; charset=utf-8
Content-Length: 15

My health is ok
```

Перевод:

> Запрос успешно обработан — `200 OK`. Тело является текстом в UTF-8 и занимает ровно 15 байт. После ответа я закрою соединение.

Строка `My health is ok` действительно занимает 15 байт.

## 8. Сервер начинает завершать разговор

```text
12345 > 49852: Flags [F.]
seq 115
ack 104
```

Сервер говорит:

> Ответ закончил. Больше ничего отправлять не буду. До свидания.

Сервер первым закрывает своё направление передачи, потому что клиент прислал HTTP-заголовок `Connection: close`.

FIN не содержит пользовательских данных, но занимает один sequence number.

## 9. Клиент подтверждает данные и FIN

Сначала клиент подтверждает тело HTTP-ответа:

```text
ack 115
```

> Все 114 байт ответа получил. Следующим ожидал бы номер `115`.

Затем клиент подтверждает FIN:

```text
ack 116
```

> Твоё завершение передачи тоже получил.

Значение стало `116`, потому что FIN занимает один номер:

```text
114 байт данных → следующий seq 115
FIN             → следующий seq 116
```

## 10. Клиент закрывает своё направление

```text
49852 > 12345: Flags [F.]
seq 104
ack 116
```

Клиент говорит:

> Я тоже больше ничего отправлять не буду. До свидания.

Обе стороны отправляют FIN, потому что каждое направление TCP-передачи закрывается отдельно.

## 11. Сервер отправляет последнее подтверждение

```text
12345 > 49852: Flags [.]
ack 105
```

Сервер говорит:

> Твоё завершение получил.

У клиента был `seq 104`. Его FIN занял один номер, поэтому сервер подтвердил `ack 105`. Теперь TCP-разговор полностью завершён.

## Весь разговор целиком

```text
Клиент                              Сервер
   |                                   |
   | -------- Хочу соединиться ------> |  SYN
   | <------- Согласен ---------------- |  SYN + ACK
   | -------- Подтверждаю ------------> |  ACK
   |                                   |
   | -------- GET /health ------------> |  HTTP request
   | <------- Байты получил ----------- |  TCP ACK
   | <------- 200 OK ------------------ |  HTTP response
   | <------- Я закончил отправку ----- |  FIN
   | -------- Подтверждаю ------------> |  ACK
   | -------- Я тоже закончил --------> |  FIN
   | <------- Подтверждаю ------------- |  ACK
   |                                   |
```

## Что означают TCP options

В SYN клиента записано:

```text
options [mss 16344,nop,wscale 6,nop,nop,
         TS val 928890934 ecr 0,sackOK,eol]
```

| Option | Назначение |
|---|---|
| `mss 16344` | Максимальный объём TCP payload, который сторона готова принять в одном сегменте |
| `wscale 6` | Масштабирование окна: значение `win` можно умножать на `2⁶`, то есть на 64 |
| `TS val` | Текущее значение TCP timestamp отправителя |
| `ecr` | Timestamp другой стороны, возвращаемый ей обратно |
| `sackOK` | Поддержка выборочного подтверждения отдельных полученных диапазонов |
| `nop` | Заполнение для выравнивания следующих options |
| `eol` | Конец списка options |

Это параметры TCP, которые обрабатывает ядро. Сервер через `recv()` получает только полезные байты HTTP-запроса, без IP-заголовка, TCP-заголовка и TCP options.

## Главное разделение ответственности

- TCP устанавливает соединение и доставляет упорядоченный поток байтов.
- HTTP определяет смысл байтов: метод, путь, заголовки, тело и статус ответа.
- TCP ACK подтверждает доставку байтов, но не успешную обработку HTTP-запроса.
- HTTP response сообщает результат обработки запроса.
- FIN завершает передачу данных в одном направлении TCP-соединения.
