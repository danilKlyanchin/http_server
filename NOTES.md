# HTTP/1.1 поверх TCP: вопросы, ответы и проверка

## Модель обмена

```text
клиент
  ↓
TCP-соединение
  ↓
байты HTTP-запроса
  ↓
разбор request line, headers и body
  ↓
выбор маршрута
  ↓
HTTP-ответ
  ↓
байты в том же TCP-соединении
```

TCP передаёт упорядоченный поток байтов и не знает границ HTTP-сообщений. HTTP определяет структуру и смысл этих байтов.

Один вызов `send()` не обязан соответствовать одному вызову `recv()`. Один HTTP-запрос может прийти несколькими чтениями, а одно чтение может содержать конец одного сообщения и начало следующего. Поэтому сервер накапливает данные в собственном буфере и определяет границы по правилам HTTP.

## Итоговые вопросы и ответы

### 1. Чем HTTP отличается от TCP?

TCP и HTTP относятся к разным уровням.

TCP предоставляет надёжный упорядоченный поток байтов между двумя сторонами:

- сохраняет порядок байтов;
- обнаруживает потери;
- повторно отправляет потерянные данные;
- управляет потоком данных;
- сообщает приложению об ошибке, если соединение перестало работать.

HTTP задаёт структуру и смысл передаваемых байтов:

- метод запроса;
- путь;
- версию протокола;
- заголовки;
- тело;
- статус и содержимое ответа.

TCP ACK подтверждает доставку байтов TCP-стеку другой стороны. Он не подтверждает, что приложение уже прочитало или успешно обработало HTTP-запрос.

### 2. Почему HTTP не заменяет TCP?

HTTP описывает формат и смысл сообщений, но сам не выполняет транспортную работу:

- не устанавливает TCP-соединение;
- не восстанавливает потерянные байты;
- не поддерживает их порядок;
- не управляет приёмным окном;
- не выполняет транспортное закрытие соединения.

HTTP нуждается в нижележащем механизме доставки. В этом сервере HTTP/1.1 работает поверх TCP. Это нельзя обобщать на все версии: HTTP/3 использует QUIC поверх UDP, но транспортный механизм всё равно остаётся необходимым.

### 3. Как определяется конец HTTP-запроса и ответа?

Сначала получатель ищет последовательность:

```text
\r\n\r\n
```

Она отделяет заголовки от тела.

Если сообщение содержит `Content-Length: N`, после заголовков нужно прочитать ровно `N` байт тела. Поэтому при keep-alive закрытие TCP-соединения не требуется для определения конца ответа.

Текущий сервер допускает запрос без `Content-Length` или с `Content-Length: 0`. Ненулевое тело и `Transfer-Encoding` отклоняются. Если поддержка тела появится позже, сервер должен будет прочитать ровно указанное количество байт, сохранив последующие байты для следующего сообщения.

В захвате первый ответ выглядел так:

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 12

Hello, HTTP!
```

Curl прочитал 12 байт тела, после чего следующие байты `GET /health HTTP/1.1` распознал как начало нового сообщения в том же TCP-потоке.

### 4. Зачем нужны headers, если данные можно передать в body?

Заголовки описывают свойства сообщения и правила его обработки, а body содержит полезную нагрузку.

Примеры:

- `Content-Length` задаёт длину тела;
- `Content-Type` сообщает, как интерпретировать тело;
- `Host` выбирает сервер или виртуальный хост;
- `Connection` управляет повторным использованием соединения;
- `Authorization` и `Cookie` передают данные аутентификации и сессии;
- `Accept` сообщает поддерживаемые клиентом форматы;
- `Content-Encoding` описывает сжатие;
- заголовки кеширования определяют возможность повторного использования ответа;
- request ID и tracing-заголовки помогают найти запрос в распределённой системе.

Одни и те же байты тела могут иметь разный смысл при разных значениях `Content-Type`.

### 5. Что изменил HTTP keep-alive в потоке сервера?

Раньше поток обрабатывал один запрос, отправлял ответ и завершался. Теперь он выполняет цикл:

```text
прочитать запрос
→ разобрать запрос
→ отправить ответ
→ снова ждать запрос
```

Поток завершается, когда:

- клиент прислал `Connection: close`;
- клиент закрыл сокет и `recv()` вернул EOF;
- произошёл таймаут;
- возникла ошибка чтения или записи;
- сервер отправил ошибку, после которой соединение нельзя безопасно переиспользовать.

В модели «один поток на соединение» бездействующее keep-alive соединение продолжает занимать поток. Большое количество таких соединений ограничивает масштабируемость этой модели.

### 6. Сохраняет ли HTTP keep-alive пользовательскую сессию? Чем он отличается от TCP keepalive?

HTTP keep-alive не создаёт и не сохраняет пользовательскую сессию. Он только позволяет передавать несколько HTTP-запросов через одно TCP-соединение.

Идентификатор пользовательской сессии обычно передаётся в каждом запросе, например:

```http
Cookie: session_id=abc123
```

или:

```http
Authorization: Bearer token
```

Одна пользовательская сессия может продолжаться через несколько TCP-соединений. Сам факт повторного использования одного соединения не означает наличие авторизованной сессии.

TCP-соединение остаётся открытым и без TCP keepalive, пока его не закроют или не обнаружится ошибка. TCP keepalive — механизм ядра, который после периода бездействия отправляет служебные probes, чтобы обнаружить недоступную удалённую сторону.

Аналогия:

- HTTP keep-alive: друзья не кладут трубку после первого вопроса, потому что хотят обсудить ещё что-то;
- пользовательская сессия: один друг сообщает код, по которому его узнают;
- TCP keepalive: во время долгого молчания телефонная служба проверяет, не оборвался ли звонок.

## Проверка маршрутов через curl

Сервер запускается командой:

```sh
./exec_server
```

Основные запросы:

```sh
curl --http1.1 -i http://127.0.0.1:12345/
curl --http1.1 -i http://127.0.0.1:12345/health
curl --http1.1 -i http://127.0.0.1:12345/unknown
curl --http1.1 -i -X POST http://127.0.0.1:12345/health
```

Ожидаемые результаты:

| Запрос | Результат |
|---|---|
| `GET /` | `200 OK`, тело `Hello, HTTP!` |
| `GET /health` | `200 OK`, тело `My health is ok` |
| `GET /unknown` | `404 Not Found` |
| `POST /health` без тела | `405 Method Not Allowed`, `Allow: GET` |

Запрос с явным закрытием соединения:

```sh
curl --http1.1 -v \
  -H 'Connection: close' \
  http://127.0.0.1:12345/health
```

Запросы для проверки keep-alive:

```sh
curl --http1.1 -v \
  http://127.0.0.1:12345/ \
  http://127.0.0.1:12345/health
```

Curl вывел:

```text
Re-using existing connection with host 127.0.0.1
```

В логах сервера оба запроса получили один идентификатор соединения:

```text
[client 1] waiting for message #1
...
[client 1] waiting for message #2
...
[client 1] waiting for message #3
[client 1] disconnected
```

После второго ответа curl сам закрыл больше не нужное соединение. Сервер в этот момент уже ожидал третий запрос.

## Просмотр трафика через tcpdump

На macOS запросы к `127.0.0.1` проходят через loopback-интерфейс `lo0`.

Вывод TCP и ASCII-содержимого пакетов:

```sh
sudo tcpdump -i lo0 -nn -s 0 -A 'tcp port 12345'
```

Значения параметров:

- `-i lo0` — слушать loopback-интерфейс;
- `-nn` — не преобразовывать адреса и порты в имена;
- `-s 0` — захватывать пакет целиком;
- `-A` — показывать содержимое в ASCII;
- `'tcp port 12345'` — оставить только TCP-трафик сервера.

Основные обозначения tcpdump:

| Обозначение | Значение |
|---|---|
| `[S]` | SYN — предложение установить соединение |
| `[S.]` | SYN + ACK — согласие и подтверждение SYN |
| `[.]` | ACK — подтверждение полученных данных или служебное состояние TCP |
| `[P.]` | PSH + ACK — передача данных |
| `[F.]` | FIN + ACK — завершение передачи в одном направлении |

В первом захвате клиент отправил `Connection: close`. После HTTP-ответа сервер первым отправил FIN. Затем клиент подтвердил FIN, закрыл своё направление и получил последнее подтверждение сервера.

В захвате keep-alive наблюдалось:

- один TCP handshake;
- два HTTP-запроса;
- два HTTP-ответа;
- одна и та же пара клиентского и серверного портов;
- непрерывные диапазоны sequence numbers;
- отсутствие нового SYN между запросами;
- закрытие соединения клиентом после второго ответа.

Диапазоны sequence numbers продолжали друг друга:

```text
клиент:
первый запрос  seq 1:79
второй запрос  seq 79:163

сервер:
первый ответ   seq 1:93
второй ответ   seq 93:188
```

Это доказывает, что второй запрос и ответ передавались в том же TCP-потоке.

## Запись и просмотр pcap в Wireshark

Запись бинарного захвата:

```sh
sudo tcpdump -i lo0 -nn -s 0 \
  -w /tmp/http-server.pcap \
  'tcp port 12345'
```

Во время записи были отправлены два запроса через одно соединение:

```sh
curl --http1.1 -v \
  http://127.0.0.1:12345/ \
  http://127.0.0.1:12345/health
```

После остановки tcpdump через `Ctrl+C` файл был открыт командой:

```sh
open -a Wireshark /tmp/http-server.pcap
```

В Wireshark использовался display filter:

```text
tcp.port == 12345
```

Через **Follow → TCP Stream** в одном потоке были видны:

```text
GET /
→ HTTP/1.1 200 OK
→ GET /health
→ HTTP/1.1 200 OK
```

Для проверки количества handshake использовался фильтр:

```text
tcp.port == 12345 && tcp.flags.syn == 1
```

Он показал два пакета: SYN клиента и SYN + ACK сервера. Это две части одного TCP handshake. Третий пакет handshake является обычным ACK и не попадает под фильтр `tcp.flags.syn == 1`.

## Практические выводы

- TCP-сегмент, вызов `recv()` и HTTP-сообщение имеют разные границы.
- HTTP/1.1 может передавать несколько сообщений внутри одного TCP-потока.
- `\r\n\r\n` завершает секцию HTTP-заголовков.
- `Content-Length` позволяет определить конец тела без закрытия соединения.
- TCP ACK подтверждает доставку байтов, но не успешную обработку запроса.
- FIN штатно закрывает одно направление TCP-передачи; обе стороны закрывают свои направления отдельно.
- HTTP keep-alive экономит новый TCP handshake, но не хранит пользовательскую сессию.
- TCP keepalive обнаруживает недоступную сторону у простаивающего соединения и не относится к HTTP-сессии.
